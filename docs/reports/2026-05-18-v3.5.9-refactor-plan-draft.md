## 1. Executive thesis (first-hand trace, 2026-05-18)

> Methodology note: §1/§1A are written from a **first-hand full read** of `dispatch.rs` (2176 LOC), `lattice/{mod,builder,walker,cost}.rs`, `lexicon/src/continuous.rs` (1740 LOC), `ranking/src/score.rs`, and `composing/src/{api,transition}.rs` — not from the parallel-agent digest. The deep read **corrected** the agent framing (see ⚠️ below) and surfaced eight findings the agent/Codex pass missed (§1A).

### What continuous input actually does (traced call chain)

`dispatch::handle` → `handle_fetch_at_pos` (`dispatch.rs:135`) runs a **5-stage pipeline**, of which **only stage 2 is modularized**:

1. **Shadow normalization** — `build_shadow_lattice` → `to_ascii_lowercase` → `canonicalize_poj_shadow` (NFD walk + `apply_normalize_to_tl_with_offsets` + `offset_aware_replace`, `dispatch.rs:1059-1227`) → `build_hyphen_shadow` (`:922`) → composes two byte-offset maps into `shadow_to_raw_end`. Pure, ~400 LOC, **lives in `dispatch.rs`**.
2. **Lattice construction** — `lattice::build_lattice` BFS DAG (`lattice/builder.rs:42`). The *one* clean module.
3. **Per-edge / per-key lexicon resolution** — span-local: `fetch_via_lexicon` → `fetch_candidates_for_keys` → `record_to_candidate` (`continuous.rs:765`) → `calculate_continuous_score` (`score.rs:443`). Walker: `fetch_walker_slot0`'s injected edge provider (`dispatch.rs:609-759`) → custom-precedence OR **`best_candidate_for_key` (`continuous.rs:736`) → the same `record_to_candidate` → the same `calculate_continuous_score`** OR OOV-synth.
4. **Two objectives over stage-3 output** — (4a) the candidate **list** (slots 1..N): 8-dim `SortKey` (`continuous.rs:969-1040`, higher-score/higher-freq wins; v3.5.8 S8 demoted `-coverage` to a weak tiebreak below score/freq). (4b) **slot 0**: `walk_best` min-`Σ edge_cost` (`lattice/walker.rs:135` + `cost/cost.rs:186`, lower-is-better), then a no-dict carve-out + per-edge recase (`dispatch.rs:768-847`).
5. **Splice + encode** — recase span-local (`dispatch.rs:230-235`) → `synth_consumed_span` gate → `retain`-dedupe slot 0 vs list by `(roman,hanji,consumed_span)` → `insert(0, slot0)` (`dispatch.rs:249-259`) → `raw_to_proto_candidate`.

### ⚠️ Correction to the agent framing

The agent inventory (and my v1 §1) called this "**two structurally unrelated scorers**". First-hand reading shows that is **wrong**: the walker is **layered on top of** the span-local primitives — `fetch_walker_slot0`'s edge provider *reuses* `best_candidate_for_key` → `record_to_candidate` → `calculate_continuous_score` (the exact primitive the span-local list uses, `dispatch.rs:686`), then applies a **second** objective (`edge_cost` min-cost over the chosen path) on top. They are not parallel competitors; they are **two stacked decision levels over one shared resolution primitive**, and the same user-frequency `FrequencyMap` is consumed at both levels (record-selection via `user_freq_boost` inside `record_to_candidate`; path-selection via `decayed_user_weight_delta` in `edge_cost`). The code defends this as "two orthogonal decision levels, no double counting" (`dispatch.rs:699-707`) — and on inspection it *is* defensible (record-disambiguation vs path-selection are genuinely orthogonal). The debt is **not** that the scorers are redundant; it is that **stages 1, 3-seam, 4b, 5 are all tangled inside `dispatch.rs` (~1490 LOC non-test)** and the two-level user-frequency coupling + the `score: -(path.cost as f32)` sign-bridge (`dispatch.rs:868-874`) survive only because comments assert the invariants. This sharpens (not weakens) the v3.5.9 thesis: **modularize the 5 stages and name the two decision levels; do NOT touch the objectives** (Codex Q5: unification = v3.6+).

Mainstream keeps one stage-per-module pipeline: McBopomofo one `ReadingGrid`+walk (`docs/references/mainstream-ime-comparison.md:40,222-229`); khiin unified segmenter+selector (`khiin-reference.md`; `:246`); librime Translator→Filter, never "compute two ways then splice" (`rime-reference.md`; `:186`). `roadmap.md:101-105` claims `composing` does not depend on `lexicon`; `dispatch.rs:22-32` imports 7 `lexicon` + 3 `ranking` symbols — doc and code diverged. v3.5.9 makes the structure tell the truth.

## 11. Documentation-lookup workflow — MANDATORY before any platform IME code (verified 2026-05-18)

Every platform slice that touches a framework/OS IME API (B3/B4/B5/B7/B9/B10 → KeyboardKit, `UIInputViewController`/`UITextDocumentProxy`, `InputMethodService`/`InputConnection`, Compose, DataStore) **MUST verify the current API against authoritative docs before writing code — never from model memory**. This was tested live, not assumed:

**Primary — `find-docs` skill → Context7 `ctx7` CLI** (confirmed working, returns real code + APIDOC blocks, no auth needed; rate-limited → `ctx7 login` or `CONTEXT7_API_KEY` for higher limits). Two-step: resolve ID, then query.

| Target | Verified Context7 library ID | Notes |
|---|---|---|
| iOS — KeyboardKit (Xcode pins range **9.7.2 ..< 11.0.0**; local clone 9.9.0 — confirm resolved version in Xcode) | `/keyboardkit/keyboardkit` | 130 snippets, High rep. Version-pin: `/keyboardkit/keyboardkit/<ver>` if listed by `ctx7 library`. Live docs already show a newer setup API (`viewWillSetupKeyboardKit()` / `setupKeyboardKit(for:)`) than this repo's `KeyboardViewController` uses — exactly why look-up is mandatory. |
| Android — official IME docs | `/websites/developer_android` (canonical) or `/websites/developer_android_training` (7254 snippets) | `InputMethodService`, `InputConnection`, `EditorInfo`, lifecycle. |
| Apple keyboard-extension primitives | resolve via `ctx7 library "apple swift uikit UIInputViewController"` per task | `UIInputViewController` / `UITextDocumentProxy` when not going through KeyboardKit. |

```
ctx7 library keyboardkit "<task-specific question>"     # step 1: resolve
ctx7 docs /keyboardkit/keyboardkit "<task-specific question>"  # step 2: fetch
```

**Local authoritative fallback (offline / version-pinned, MAIN repo only — gitignored, NOT in worktrees):**
- `references/KeyboardKit-Documentation/` — DocC archive pinned to the cloned KK version (consult `documentation/keyboardkit/` JSON; the `mainstream-ime-comparison.md` rule already says "treat as gospel before WebSearching").
- `references/keyboardkit9.9.0/Sources/KeyboardKit/` — actual KK source to read a symbol when docs are ambiguous.
- Android has **no** local clone → use `ctx7` / `WebFetch https://developer.android.com/develop/ui/views/touch-and-input/creating-input-method` (the CLAUDE.md-pinned URL).

**Secondary — `WebFetch`/`WebSearch`** (deferred tools) for a specific Apple/Android doc URL or release notes when Context7 lacks coverage.

**Per-implementation gate (add to each platform slice's PR checklist):** state which API was looked up, via which source, and the doc version/date — same discipline as the Codex sandwich. Aligns with global `CLAUDE.md` ("prefer online docs over pre-trained knowledge; verify current APIs/versions") and `feedback`-online-sources; §11 makes it a hard per-slice gate, not a default.
