## 1. Summary

The 2026-09-30 audit removed the four-way commit resolver, the desktop settings-app twins and the dispatch user-data façade. What is left is **the second tier of the same pattern**: the phones still resolve next-word prediction taps and TPS keystrokes themselves (the engine has `commit_text.rs` and `TpsKey` for exactly that), the Dictionary-tab search is orchestrated three times over four engine ops, and the three desktop shells each carry their own global-action and symbol-picker flow on top of desktop-core. Three of these twins have already drifted where a user can see it: the mobile Custom Dictionary list has no paging and its own substring filter (word #101 is unreachable, `tsui2` does not find `tsuí`), the mobile Add/Edit dialog requires Hanji and swallows engine refusals while all three desktops accept romanization-only words, and a custom word shows MOE / Chhoe lookup buttons on phones but not on desktop.

Inside the engine the crate graph is clean (no upward edge, no dev-dep cycle), but `dispatch` still runs composing's `FetchAtPos` on two parallel paths and reaches five composing internals, and `composing/continuous.rs` (1,716 production lines) holds three concerns. The dead surface is wire data rather than ops: four `CandidateMessage` fields and the whole `script_kind` derivation chain are set, decoded and never read; one phonetics op (`TlNumericToTps`) has no caller; a 222-line test pins a pre-R6 TPS wire no bridge sends.

Docs drifted in 50 places; one would mislead a contributor (`linux-release.md` claims Linux packages build on every PR; the workflow runs nightly + dispatch only).

**Recommended first rounds:** docs drift (admin lane, same day) → dead surface (delete-only) → the two mobile Custom Dictionary parity fixes → dictionary search as one engine op → mobile prediction-tap and TPS-key commit paths into the engine. Those five remove the largest duplication and every observable drift before the cohesion and desktop-shell rounds touch structure.
