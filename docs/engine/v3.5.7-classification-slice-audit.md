## 1. Domain definition

The slice migrates **input classification** to the Rust shared core:

- `is_hanzi(text)` — true iff `text` contains any CJK Unified Ideograph (Unified + Extensions A–E).
- `contains_numeric_tone(text)` — true iff `text` contains any ASCII digit other than `'0'`, `'1'`, `'4'`.
- `classify_input(raw)` — returns `(InputType, search_key)`. Pipeline: `is_hanzi` → `phonetics::has_tone_marks` → `contains_numeric_tone` → search_key built via `phonetics::contains_tps`/`tps_to_tl` (TPS path) or pass-through.

Out of scope (locked, see §8): capitalization (`CaseTransformer`, `CandidateProcessor.capitalize` / `startsWithRomanLetter`), `CharacterInputPipeline`, `CustomDictionaryDerivation`. All already either thin shims or rejected per Codex round 1 D3/D4 + round 2.

## 4. Cross-platform divergences

### 4.1 D-1 — Tab3 hanzi range divergence (PARITY CORRECTION)

| Site | Today | After v3.5.7 |
|---|---|---|
| iOS `DictionarySearchService.swift:67` | 6 ranges via `CandidateProcessor.isHanzi` (Unified + A–E) | 6 ranges via Rust `is_hanzi` (canonical) |
| Android `DictionarySearchViewModel.kt:97` | Inline `query.any { ... }` syntactically lists Unified + A + B, but **effectively only Unified + A** — Kotlin `Char.code` is a 16-bit UTF-16 code unit (0–65535), so the `0x20000..0x2A6DF` Extension B clause is dead code | 6 ranges via Rust `is_hanzi` (canonical, iterates Unicode codepoints) |

**Effect on user-visible behavior**: Hanji codepoints in Extensions B/C/D/E (`0x20000–0x2CEAF`, ≈ 52,880 codepoints by the documented A–E blocks; C/D/E alone = 10,160) typed into Tab3 search on Android currently are NOT recognized as Hanji — the lookup falls into the romanization branch (always returns empty). After v3.5.7 they route to the hanzi-search branch (result count then depends on dictionary data; previously they always took the wrong branch).

This is a `rules/cross-platform-alignment.md §1b` parity-correction tier change. Impact scope: low typing frequency (Extensions B–E are mostly historical / rare-character-set), but the silent-divergence + always-wrong-branch behavior is the bug.

### 4.2 D-2 — Classifier internal CJK ranges (NO divergence)

iOS `CandidateProcessor.isHanzi` and Android `AutocompleteInputClassifier.isHanzi` (private) both use the identical 6 ranges. The classifier path is consistent; only Tab3's separate inline check diverged.

### 4.3 D-3 — `containsNumericTone` (NO divergence)

iOS `containsNumericTone` and Android `containsNumericTone` (private in classifier) both gate on ASCII digits excluding `'1'`, `'4'`, `'0'`. Identical logic. Documented rationales differ (Android: "0 reserved for slot-0 composing candidate"; iOS: "0 invalid input") but that's prose, not behavior. Rust will encode behavior-only docstring per Codex round 2 D2.

## 5. INVARIANT labels (added in this slice)

Authored against `docs/architecture/behavioral-invariants.md`. New umbrella label with named subcases per Codex round 2 D5.

### `INVARIANT_LEX_INPUT_CLASSIFICATION`

> Input classification is purely structural: same `raw` string ⇒ same `(InputType, search_key)` tuple regardless of input mode, settings, or platform. Subcases below pin the behavior.

#### `INVARIANT_LEX_INPUT_CLASSIFICATION_HANZI_RANGE`

> `is_hanzi(text)` returns `true` iff `text` contains at least one Unicode codepoint in any of:
> - CJK Unified Ideographs `0x4E00–0x9FFF`
> - CJK Extension A `0x3400–0x4DBF`
> - CJK Extension B `0x20000–0x2A6DF`
> - CJK Extension C `0x2A700–0x2B73F`
> - CJK Extension D `0x2B740–0x2B81F`
> - CJK Extension E `0x2B820–0x2CEAF`
>
> Extensions F/G/H/I/J are **explicitly excluded** at this slice. Future expansion is a separate behavior change, not a parity correction.

#### `INVARIANT_LEX_INPUT_CLASSIFICATION_NUMERIC_TONE_SET`

> `contains_numeric_tone(text)` returns `true` iff `text` contains at least one ASCII digit in `{'2','3','5','6','7','8','9'}`. Digits `'0'`, `'1'`, `'4'` are NOT numeric tone markers.

#### `INVARIANT_LEX_INPUT_CLASSIFICATION_PRECEDENCE`

> `classify_input(raw)` resolves `InputType` via short-circuit precedence:
> 1. `is_hanzi(raw)` ⇒ `InputType.Hanzi`
> 2. `phonetics::has_tone_marks(raw)` ⇒ `InputType.RomanWithTone`
> 3. `contains_numeric_tone(raw)` ⇒ `InputType.RomanWithTone`
> 4. otherwise ⇒ `InputType.RomanWithoutTone`

#### `INVARIANT_LEX_INPUT_CLASSIFICATION_SEARCH_KEY`

> `classify_input(raw).search_key` is:
> - `phonetics::tps_to_tl(raw)` if `phonetics::contains_tps(raw)` is `true`
> - `raw` otherwise (no transformation when not TPS)
